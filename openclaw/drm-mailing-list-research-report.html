Key Patterns for Full DRM Driver Submissions

▼

🔴 Pattern 1: Atomic Modesetting is MANDATORY

  • All new drivers MUST use atomic modesetting
  • No legacy modesetting callbacks accepted
  • Use drm_atomic_helper_* functions exclusively
  • Implement atomic_check and atomic_commit

🔵 Pattern 2: Use Standard Helpers

  • GEM/Buffer: Use DRM_GEM_DMA_HELPER for SoC display drivers
  • KMS Helpers: Use DRM_KMS_HELPER and DRM_DISPLAY_HELPER
  • Bridge/Panel: Use DRM_BRIDGE_CONNECTOR and DRM_PANEL_BRIDGE

🟢 Pattern 3: DT Bindings First

  • Submit DT bindings BEFORE or WITH the driver
  • Bindings reviewed separately by dt-bindings maintainers
  • Use YAML schema format (.yaml files)
  • Expect binding review to take 1-3 weeks

🟡 Pattern 4: Driver Directory Structure

drivers/gpu/drm/vendor/
├── Kconfig
├── Makefile
├── vendor_drv.c      # Main driver, probe, platform
├── vendor_crtc.c     # CRTC implementation
├── vendor_plane.c    # Plane implementation
├── vendor_encoder.c  # Encoder (if needed)
├── vendor_output.c   # DP/eDP/HDMI output
└── vendor_drv.h      # Shared header

🟣 Pattern 5: Patch Series Order

  1. DT bindings (1-2 patches per component)
  2. Core driver infrastructure (Kconfig, Makefile, probe)
  3. KMS objects (CRTC, planes, connector registration)
  4. Output drivers (DP, eDP, HDMI)
  5. DT additions (DTSI files for SoC, DTS for boards)
  6. MAINTAINERS update

⚪ Pattern 6: Patch Size Limits

  • Individual patches: ~500 lines max preferred
  • Split large files logically (CRTC in one patch, planes in another)
  • Each patch must compile and be bisectable
  • 15-40 patches typical for full driver

Common Mistakes to Avoid

▼

❌ Code Mistakes

  • Not using atomic helpers — Use drm_atomic_helper_* functions
  • Reinventing GEM — Use DRM_GEM_DMA_HELPER for SoC
  • Legacy DPMS callbacks — Use atomic enable/disable
  • Hardcoded timings — Use OF videomode helpers
  • Missing error paths — Handle all failure cases

⚠️ Process Mistakes

  • Submitting incomplete drivers — Basic functionality must work
  • Not running checkpatch — Fix all errors before submission
  • Large monolithic patches — Split logically
  • Ignoring review comments — Address everything
  • Long response delays — Respond within 1-2 weeks

✅ What Gets Accepted (with revisions)

  • Minor code style issues
  • Missing error handling
  • Suboptimal helper usage
  • Documentation gaps
